# 一次性定时：实施计划

状态：已实现，待验收。重复调度已经在当前代码里（对照 `596abba`）。约束仍以 [定时任务：需求与原则](./schedule-requirements.md) 为准；和重复任务不同的几条在该文「一次性任务」一节。本文只写怎么做。

用户故事是验收。后面的章节说明怎样做到。已定决策不再另开待定。

## 1. 用户故事

### US-1 五分钟后回来看一次

作为正在这条对话里的用户，我要说「5 分钟后看这次编译」，以便到点在同一条对话里看到结果。

验收：

- 保存的是一个绝对时刻。到点跑完就停，不会每 5 分钟再跑。
- 没说时刻就拒绝，不替用户选一个默认间隔。
- 短于 1 分钟的延迟拒绝。时钟最长约 60 秒才对一次表，所以到点可能晚大约 1 分钟。
- 保存后不立刻跑。
- 已保存的指令里写明要查的对象（例如提交、仓库、要回报的项）。
- 创建不需要批准。卡片上的开关是用户的控制：开着才会跑，关掉是暂停。相对延迟在保存前冻结成绝对时刻；卡片和保存的是同一个本地时间，以及「只一次」。保存时这个时刻已经过去则拒绝创建，不从当时重新计时。

### US-2 在输入框上方看住这张卡片

作为用户，我要在输入框上方固定看到卡片，以便消息变多后仍能快速找到它，知道何时会跑、跑什么，并能先关掉或删掉。

验收：

- 卡片上有名称、创建时冻结的说法（例如「5 分钟后，只一次」）、已保存的指令、倒计时、本地时间。
- 倒计时随页面时间变，不另起一个会触发运行的定时器。
- 开关开着才会跑。关掉是暂停。删除后卡片变为「已删除」，不能恢复。
- 侧栏和这张卡片读的是同一条任务，说法一致。

### US-3 对话还在忙时不要把这一次作废

作为用户，我要在到点时如果这条对话还在跑，这次检查等到空闲再开始，以便不会因为多说了一句话就失去结果。

验收：

- 正忙时不插入当前这一轮，也不排队。
- 空闲后仍跑原来那一次。
- 等待期间不每分钟写一条「已跳过」。
- 原时刻过了 30 分钟仍忙：写一条跳过说明，然后结束，没有下一次。
- 每天、每小时的重复任务不变：这一次跳过，下一个计划点还在。

### US-4 跑完后卡片仍然容易找到

作为用户，我要在结束后仍能看到当初设了什么、上次何时跑的，以便回头核对；检查结论在对话正文里。

验收：

- 卡片继续固定在输入框上方，不随 transcript 滚走，也不写进 transcript 当第二份事实。
- 开关关着。没有下次。再打开也不会重新计时。
- 这轮运行成功时，卡片写「已完成」和上次运行时间。指令原文还在。
- 「已完成」只表示这次调度跑完了。打包失败、测试失败写在另一条自动来源的回复里。

### US-5 没跑成也没有下一次

作为用户，我要在失败、停滞、被停下、跳过或结果不明时看到这次的真实状态，以便知道它不会自动再跑。

验收：

- 卡片不写「已完成」，改写这次运行的状态。
- 没有下次。打开开关不产生新时刻。
- 结果不明有一条说明，并且不会被当成「没跑过」再派一次。

### US-6 应用没开着，醒来只补这一次

作为用户，我要在重新打开应用后，如果错过了那个时刻，仍然只补跑这一次，以便还能看到结果。

验收：

- 对话空闲时补这一次，不论晚了多久。
- 不补出第二次。
- 暂停期间错过的时刻不补。恢复时，时刻还在将来就回到那个时刻；时刻已过则保持暂停，不立刻跑。

### US-7 原来的重复任务照旧

作为已经在用每天摘要的用户，我要一次运行结束后任务继续按原来的频率等下一次，以便「只看一次」不会改掉已有任务。

验收：

- `weekly` 和 `interval` 的领取、正忙跳过、失败后等待下一次，都与现在相同。
- 重复任务的卡片和侧栏仍显示下一次时间。

## 2. 目标与非目标

目标：在现有时钟、领取、派发和 `schedule` 工具上增加「只跑一次」。对话里用一张实时卡片表示它从设定到结束的状态。

非目标：

- 第二套时钟、cron、对话进程里的定时器、系统闹钟。
- 「每隔几分钟直到有结果再停」，以及只在有变化时提醒。
- 改重复任务的正忙、补跑和失败策略。
- 把检查结论写进卡片。结论仍是这轮的助手回复。
- 手机上画这张卡片。手机仍读同一条 transcript，后台仍用现有的运行结束通知。
- 创建后立刻跑。立刻跑仍是单独的 `run_now`。

## 3. 已定决策

1. **第三种规则，不是新调度器。** `once` 走现有的 `Clock`、`Store.claim`、`Dispatch`、`Recorder`。
2. **时刻在保存前冻结成 UTC。** 相对延迟不入库。一次性任务不走批准，卡片开关是用户的控制。入库的是保存时冻结的绝对时间，以及当时算好的说明文字。说明文字之后不再改。重复任务的创建批准不变。
3. **正忙不领取。** 领取会占住 `(schedule_id, slot_at)` 并清掉下一次。唯一一次被领走就不能再领。正忙时让它继续到期。
4. **正忙的宽限是 30 分钟，从原时刻算。** 这是代码常量，不是设置项。只约束「对话正忙」。应用睡着后醒来、对话已经空闲：仍补这一次，不受这 30 分钟限制。
5. **宽限内不写跳过说明。** 放弃时写一条。
6. **领取时清掉 `next_run_at`，任务仍是 `active`。** 用户看见「已完成」要等这轮进入终态。时钟只领 `active` 且有下次时间的行，所以运行期间不会再响。
7. **终态用任务状态 `completed` 表示「不会再跑」。** 卡片上的字看最近一次 `schedule_runs` 的状态。`disabled` 仍只表示对话没了。
8. **开关不能复活已经结束或时刻已过的一次性任务。** 删除仍可用。
9. **卡片是投影。** 当前对话的一次性任务固定显示在输入框上方，避免消息变多后难以找回。实时字段从 `schedules` 和最近一次 `schedule_runs` 读，不写进 transcript 当第二份事实。倒计时在页面上用 `next_run_at` 计算。
10. **任务一变就广播。** 创建、暂停、恢复、删除、领取、放弃、终态都发到现有的 `runtime:schedules`。现在只有写进 transcript 的说明会广播，面板没打开时对话不会更新。
11. **确定没派发才能放回。** `Coordinator` 只有在确认没有持久化 inbound、没有启动 Runner，并成功释放这次 `request_id` 的 `OperationReceipt` 后，才返回可放回的 `:busy`。receipt 释放失败、进程在接受边界崩溃，或结果无法证明时，一律是 `delivery_unknown`，不放回。
12. **一次性终态是一个事务。** `schedule_runs` 的终态和父任务的 `completed + next_run_at = NULL` 在 Store 的同一事务中提交。重复事件幂等；广播只在提交成功后发送。

## 5. 规则

保存后的规则：

```json
{"kind": "once", "at": "2026-10-11T14:58:00Z", "label": "5 分钟后，只一次"}
```

工具原始入参二选一，由可信运行时的 `prepare_once` 边界折算，模型不写 `label`：

- `{"kind": "once", "in_minutes": 5}`：`at = prepared_at + 5 分钟`，`label` 为「5 分钟后，只一次」。`in_minutes` 不入库。
- `{"kind": "once", "at": "2026-10-11T22:58"}`：没有时区偏移的本地时间，用这条任务的 IANA 时区解释，`label` 为本地时间加「，只一次」。

`prepared_at` 是运行时开始准备这次工具调用的时间。保存前把原始规则替换成 canonical 的 UTC `at + label`。这次调用之后不再用当前时间重算。

两者都给、都没给、`in_minutes` 小于 1、或折算后的 `at` 距 `prepared_at` 少于 1 分钟：拒绝。不默认成间隔。保存时若冻结的 `at` 已经过期，也拒绝且不写任务；不能改成“再等五分钟”。

`Rule` 对 `once`：

- `next_after`：`at` 仍在将来则返回它，否则 `:in_the_past`。
- `latest_due`：`at` 已到则这一次就是计划点，`missed` 为 0，下次为空。不向前走第二步。
- `upcoming`：将来只返回这一个时刻，否则空列表。
- `describe`：返回 `label`。没有 `label` 时用本地时间加「，只一次」。

不改表。`rule` 已是 map，`status` 已是字符串。

## 6. 运行

### 6.1 到点

`Clock` 看到到期的 `once` 时：

1. 对话正忙，且现在早于 `at + 30 分钟`：留下，本拍结束。不插入 `schedule_runs`，不写 transcript。
2. 对话正忙，且已过这 30 分钟：一次事务里插入 `skipped`（`reason` 为 `busy`，`slot_at` 为原来的 `at`），把任务改为 `completed`、`next_run_at` 清空，并写一条跳过说明。
3. 对话空闲：`claim`。版本更新把 `next_run_at` 设为空，状态保持 `active`，并插入这一次的 `schedule_runs`。然后交给现有的 `Dispatch`。

空闲判断和领取之间对话变忙有两条确定路径：

- `Dispatch` 在调用 Coordinator 前已经看到 busy：还没有 receipt，直接走 Store 的放回事务。
- Coordinator 在接受竞争中看到 busy：先确认没有持久化 inbound、没有启动 Runner，再释放本次 `request_id` 的 receipt；只有释放成功才返回可放回的 `:busy`。

receipt 释放仍在 `OperationReceipt` 的同一把锁内完成：只有 `request_id`、fingerprint 和 `reserved` 状态都匹配时才删除这条预留。记录不存在、已是 `unknown` / `completed`、fingerprint 不同或写盘失败，都不算释放成功。`require_idle?: true` 的调用只有完成这一步后才能向 Dispatch 返回 `{:error, :busy}`；否则返回 `{:error, :delivery_unknown}`。

收到可放回的 `:busy` 后，`Dispatch` 再确认运行仍是 `claimed` 且没有 `run_id`，一次事务里删掉这次领取、把 `next_run_at` 放回 `at`、状态放回 `active`。已经 `started`、receipt 释放失败、调用超时或任何结果不明都不放回；它们按 `unknown` 终结。放回后继续按 6.1 的正忙规则等，仍使用同一个由任务和 `at` 导出的 `request_id`。

应用醒来时对话已经空闲：走第 3 步，即使 `at` 早已过去。这就是 US-6 的那一次补跑。

`run_now` 产生的 `manual` run 不属于上面的唯一计划点。它正忙或结束时只记录这次手动运行的结果，不放回、领取或完成父任务，也不改变原来的 `next_run_at`。

### 6.2 结束后

`Recorder` 在一次性任务的计划 run 进入终态时调用 Store 的单一终态接口。一个事务里把 run 写为 `completed` / `failed` / `stalled` / `halted` / `cancelled`，同时把父任务写为 `completed` 并保证 `next_run_at` 为空。事务提交后才广播 `schedule_changed`。`manual` run 只结束自身，不完成父任务。

领取之后、派发之前崩溃：恢复走同一个终态接口，在一个事务里把这次运行标成 `unknown`，同时把一次性任务改为 `completed`，并保留现有的「结果不明，不会自动重跑」。不把 `next_run_at` 放回去。

终态接口按 `schedule_runs.id` 或 `run_id` 定位并幂等：run 和父任务都已是目标终态时返回成功；发现 run 已终态但父任务仍是 `active + next_run_at = NULL` 时补齐父任务，修复旧版本或中断留下的半状态。重复任务仍只更新 run。

重复任务的 `finish_by_run_id` 不改父任务状态，也不清下一次。

### 6.3 暂停、恢复、删除

- 暂停：只允许 `active` 且 `next_run_at` 仍存在的任务；改为 `paused`，`next_run_at` 清空，`at` 留在规则里。已经 `claimed` / `started`、`completed` 或 `disabled` 时拒绝，不能用 `pause` 覆盖真实终态。
- 恢复：只允许 `paused`。`at` 仍在将来则回到 `active`，`next_run_at` 就是这个 `at`；`at` 已过则保持 `paused` 并返回错误，不跑。`completed` 不能先暂停再恢复。
- 删除：现有删除。卡片变为「已删除」。

## 7. 卡片

固定在当前对话输入框上方，用任务 `id` 读库，不随 transcript 滚动。库里没有这条，或已经删除：显示「已删除」。

| 条件 | 开关 | 卡片上的话 |
| --- | --- | --- |
| `active`，下次在将来 | 开，可关 | 冻结说法、倒计时、本地时间 |
| `active`，下次已到，还没有运行行 | 开，可关 | 冻结说法、对话正忙，空闲后开始、最迟到原时刻加 30 分钟 |
| `active`，下次为空，最近一次为 `started` | 关，不可开 | 没有下次 · 运行中 |
| `completed`，最近一次为 `completed` | 关，不可开 | 已完成 · 上次运行于何时 |
| `completed`，最近一次为失败、停滞、halted、取消、跳过、不明 | 关，不可开 | 这次的状态 · 上次运行于何时。不明沿用「不会自动重跑」 |
| `paused`，`at` 还在将来 | 关，可开 | 已暂停，以及那个时刻 |
| `paused`，`at` 已过 | 关，不可开 | 时刻已过，保持暂停 |
| 已删除 | 无 | 已删除 |

「上次运行于何时」用最近一次 `schedule_runs` 的更新时间，在页面上显示成相对时间。指令原文始终来自任务行，直到删除。

侧栏对 `once` 用同一张表，不另写一套状态词。

`WorkspaceLive` 订阅已在。补上 `{:schedule_changed, conversation_id}`：当前对话不论侧栏是否打开都重新读取任务。创建、暂停、恢复、删除、领取、放回、放弃、终态都发这条消息。

## 8. 工具

`schedule` 的说明写明：单次检查用 `once`；`interval` 是一直重复。指令要包含具体对象。定时运行、委派和 thread 仍不能改调度。

`once` 的创建和改时间不进入批准。用户看到的是对话里的卡片，开关开着才会到点跑。保存前调用 `prepare_once`，工具参数换成 canonical 的 UTC `at + label`。卡片和侧栏对这份规则调用 `upcoming`，得到 0 或 1 个时刻；文字是 `describe` 的结果和这一个本地时间。执行使用同一份 canonical 参数，不重新解释 `in_minutes`。

重复任务的 `create`、改频率和 `run_now` 仍按原策略批准。

| US-1 | 默认频率 | 没有 `at` 也没有 `in_minutes`，创建失败，没有行 |

| US-1 | 保存时重新计时 | `in_minutes: 5` 在保存前冻结为绝对 `at`；推进测试时钟再保存，保存的仍是第一次冻结的 `at`，不从当时加 5 分钟 |

| US-1 | 立即运行吃掉计划点 | `run_now` 的 `manual` run 无论完成、失败或正忙，都不改变一次性任务原来的状态和 `next_run_at`，也不能把暂停或已结束任务恢复为 `active` |
| US-3 | 正忙把唯一一次领走 | 到点且对话忙：没有 `schedule_runs`，`next_run_at` 仍是 `at`；下一拍仍可领 |
| US-3 | 等待刷屏 | 忙着的 10 个 tick 里 transcript 没有新的跳过说明 |
| US-3 | 宽限用尽 | `at` 之后 30 分钟仍忙：一行 `skipped` / `busy`，任务 `completed`，一条说明 |
| US-3 | 检查空闲和领取之间变忙 | 已插入但仍是 `claimed`：Coordinator 确认无副作用并释放 receipt，放回后以同一 `request_id` 可以再领并只启动一次；`started` 不放回 |
| US-3、US-5 | receipt 释放失败 | Coordinator 无法确认或释放 receipt：不放回，run 和父任务以 `unknown` 终结，没有新的 Agent run |
| US-6 | 睡过了头 | 把现在拨到 `at` 之后数小时，对话空闲：只领取一次 |
| US-6 | 暂停后补跑 | 暂停越过 `at` 再恢复：仍是 `paused`，没有运行 |
| US-4、US-5 | 成功和失败的用词 | 运行 `completed` 时卡片为已完成；`failed` / `unknown` 时不用「已完成」，且父任务都是 `completed`、没有下次 |
| US-4、US-5 | 终态只写了一半 | 在终态事务的 run 更新和父任务更新之间注入失败：两边都回滚；重试后两边一起进入终态，广播只出现提交后的状态 |
| US-5 | 崩溃后再跑 | 停在 `claimed`：重启后运行是 `unknown`，任务 `completed`，没有新的 run |
| US-5 | 已结束后暂停 | 对 `completed` 的一次性任务调用 `pause`：返回错误，任务仍为 `completed`，卡片仍显示真实运行结果 |
| US-7 | 重复任务被改掉 | `interval` 在正忙时仍跳过并保留下一次；失败后仍是 `active` |
| US-2 | 卡片被消息冲走 | 增加多轮消息后，卡片仍固定在输入框上方；同一条任务在卡片和侧栏上的状态词相同；删除后卡片为已删除 |

测试时钟继续用 `:handbean` 的 `:schedule_now`。`once` 的 30 分钟从规则里的 `at` 算，不从「第一次发现正忙」算。

## 10. 分期

| 阶段 | 目标 | 范围 | 不做 | 验收 |
| --- | --- | --- | --- | --- |
| P0 | 能表示并算出唯一一次 | `Rule` 的 canonical 校验、`prepare_once`、`next_after`、`latest_due`、`upcoming`、`describe` | 领取、界面 | US-1 的时刻、冻结、过期与拒绝；不产生第二次 |
| P1 | 到点只领一次，结束后不再领 | `Clock` 的忙闲分支、`claim` 清空下次、Coordinator receipt 安全释放、放回、放弃、Store 原子终态、不明恢复、状态守卫 | 工具文案、卡片 | 第 9 节里 US-3、US-5、US-6、US-7 各行 |
| P2 | 模型不会建成重复任务 | 工具说明、schema、保存前 canonical 化；`once` 不进入批准 | 卡片 | 创建直接落盘，时刻和「只一次」与卡片一致 |
| P3 | 对话里看得到从设定到结束 | 输入框上方的固定卡片投影、`schedule_changed`、侧栏同一套词 | 手机卡片 | US-2、US-4：开关、删除、终态用词、倒计时不触发运行 |

P0 不放进会触发的路径。P1 合入前，`once` 规则校验可以存在，但工具还不能创建它。

## 11. 完成定义

- US-1 到 US-7 的验收都有第 9 节或第 10 节对应的自动化测试。`mix test --exclude slow` 通过，`mix compile --warnings-as-errors` 没有新的 warning。
- 实测一条：在工作区对话里说「5 分钟后检查某次提交」，不出现批准，卡片直接出现且开关开着；时刻未到没有运行；用测试时钟拨过时刻且对话空闲，transcript 里有一轮 `Automatic · schedule`；卡片变为已完成，开关关着，没有下次；再拨一个间隔，没有第二轮。
- 已知限制写进结果：应用没在运行时不响；醒来只补这一次；到点可能晚约 1 分钟；正忙超过 30 分钟则跳过并结束；手机没有这张卡片。
