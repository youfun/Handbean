# 定时任务：需求与原则

在一个已有对话里，到点开始一轮无人值守的 Agent 运行，并把结果写回这个对话。第一版的例子是定时取新闻、整理摘要；调度器不认识 Twitter，也不内置任何技能。

这是约束，不是实施计划。

## 要解决的事

- 用户或当前对话里的 Agent 可以创建、查看、暂停、恢复、修改、删除绑定在**这个对话**上的定时任务。
- 到点后，在这个对话里追加一条自动来源的消息，并由此开始一轮新的运行。结果留在同一条 transcript 里，不另开隐藏对话。
- 技能决定“取什么、怎么写”。调度器只决定“何时、在哪个对话、用哪段已保存的指令开始一轮”。`follow-builders` 这类技能是调用方，不是调度实现。
- 应用没在跑时不承诺触发。进程再次起来时，按下面的补跑规则处理，而不是靠系统 crontab、手机闹钟或对话进程里的定时器。

## 不解决的事

- 不把 `Handbean.Jobs`、`device_alarm`、系统 crontab、Quantum/Oban 或某个对话的 Session 当成时钟。
- 不承诺手机进程死后仍会响。不把打开系统闹钟界面算作已调度。
- 不承诺无人值守时用浏览器登录、搜索 Twitter 或操作桌面。取数失败是这一轮的结果，不是调度器的重试风暴。
- 不重放错过的每一次。不把定时消息插进用户正在进行的那一轮。
- 不引入第二套对话存储、第二个 Agent runtime，或另一份 UI 投影。

## 用户可见行为

- 一条定时任务属于一个对话、一个工作区。一个对话可以有多条，彼此独立。
- 创建时必须有明确的重复频率或一次时刻、时区和要执行的指令。Agent 不得把“帮我盯着”解释成默认频率。重复任务比用户刚刚同意的更密，必须再次得到明确同意。
- 重复频率和一次时刻都用用户当时的 IANA 时区解释，不把裸 UTC 当作用户看到的时间。
- 保存或修改规则只计算下一次，不因此立刻跑。立刻跑是单独动作，不占用、不推迟下一次计划点。
- 重复任务暂停后不再触发，也不补跑暂停期间错过的点；恢复后从恢复时刻重新计算下一次。一次性任务的恢复规则见「一次性任务」。
- 删除对话、或对话不可再运行时，它的定时任务不再触发。
- 每一轮在对话里显示为已有的自动来源（`Automatic`），并计入这个对话的正常用量。用户能看出哪一次跑了、跳过了、结果不明。
- 定时运行中的模型不能创建、加密、改目标、暂停或删除定时任务。只有用户所在的交互回合可以改。技能或抓到的网页不能借这一轮改调度。

## 运行时契约

- 唯一入口仍是 `Coordinator.add_message/3`。定时触发不直接调用 `Agent.run`，不写第二份入站持久化。
- `conversation_id`、`run_id`、`request_id` 不能互相替代。一次计划点的 `request_id` 由任务身份和该次计划时间稳定导出。重复触发返回原回执，不另开一轮。
- 这是 at-most-once，不是 exactly-once。领取本次触发权之后、Coordinator 接受之前崩溃，结果是 `delivery_unknown`：保留为不明，不自动再派一次。调用方不得把不明当成“没跑过”重试。
- 定时消息只有在对话 idle 时才接受，并且必须是新的 run。不得作为当前 run 的 `:steer` 或 `:follow_up` 入队。重复任务在对话正忙、正在等审批、或上一次同一任务的运行尚未结束时，本次跳过并留下原因；不插入，不堆积。一次性任务正忙时不领取、不跳过，见「一次性任务」。
- `source` 属于无人值守通道，和 webhook/SNS/CLI 一类，不和 LiveView/native 一类。进展守卫和轮数上限按无人值守通道执行。
- `awaiting_approval` 不是终态。定时运行没有人会点批准。需要批准的工具可以由工作区的自动审查代替人工批准；自动审查未开启、无法判断，或是必须人在场的桌面控制时，不在定时运行中提供。模型仍请求时，本轮结束并在对话里说明，任务保持原状态，等待下一次计划点。上次的批准不能缓存成这次的许可。
- 模型和工具以触发时的工作区策略为准，不复用已经消失的页面连接，也不在禁止名单里静默换一个模型。当时没有合法模型：跳过并说明。
- 指令和用户偏好在创建时保存。技能正文在触发时读取，以便技能更新生效。触发时不把“刚才聊到哪”当成任务内容；需要的上下文必须写在已保存的指令里。历史摘要仍在这条 transcript 中，供模型自己读。
- 重复任务的一轮失败、超时、停滞或被守卫停下：记下这次结果，任务仍按原频率等待下一次。不立刻重试，不因为连续失败擅自停用。一次性任务没有下一次，见「一次性任务」。
- 进程起来或从睡眠恢复时，用持久化的下次时间对当前时间判断，不用“定时器有没有响过”判断。多个计划点已经到期时，每条任务最多补**最新一个尚未领取**的点，更早的点记为跳过。

## 一次性任务

实施见 [一次性定时](./schedule-once-plan.md)。下面只约束 `once`，重复任务仍按上文。

- 创建时要有明确的一次时刻，并且不需要批准。相对延迟在保存前由可信运行时冻结成绝对时间。卡片和最终保存必须使用同一个绝对时间，不能在保存后重新从当时起算。保存时该时刻已经过去则拒绝创建，不擅自顺延。没有时刻就拒绝，不设默认间隔。用户用卡片上的开关决定到点会不会跑。
- 保存后不立刻跑。
- 到点时对话正忙：不领取，不入队，也不每拍写一条跳过。对话空闲后仍跑这一次。原时刻过了 30 分钟仍忙：写一条跳过并结束。
- 应用没在跑：醒来后若对话空闲，补这一次，不论晚了多久。不补第二次。
- 跑完、失败、跳过或结果不明：都没有下一次。
- 暂停后再恢复：时刻还在将来就回到那个时刻；时刻已过则保持暂停，不立刻跑。
- 卡片上的「已完成」表示这轮调度结束，不表示指令里要检查的事情成功。

## 开发原则

- **时钟和对话分开。** 对话 Session 可以不在。时钟是应用级的单写者，只负责到点和领取，不负责跑模型，也不把全部数据库 IO 串行进自己。
- **领取必须原子。** 单次写入原子不等于“先读再决定再写”原子。同一计划点只能有一个领取者；没领取到的一方不得派发。计数、状态和派生的下次时间不能分属可以互相覆盖的更新。
- **持久化在进程外。** 重启后仍能知道下次时间、上次领取和不明结果。对话正文继续走现有 transcript；定时记录本身要能按下次时间查询，不靠扫对话 JSON。
- **技能不拥有时钟。** 技能可以指导 Agent 调用定时能力。它不能写 crontab、改监督树，或在回合里用进程定时器冒充已调度。
- **抓取和调度分开。** 调度器不解析新闻、不登录网站、不重试外部接口。外部内容是不可信参考，不是给运行时的指令。原生或外部进程崩溃不得拖垮 BEAM；超时和重建是边界，不是“资源已经封死”的承诺。
- **缓存不得吃掉当时的检查。** 可以复用技能文件和公共配置。不能复用上一次的批准、模型许可或“对话正好空闲”。
- **身份由运行时注入。** 工具参数不能指定对话、工作区或跨工作区授权。Agent 只能操作当前对话的定时任务。
- **退化要可见。** 跳过、补跑、不明、无合法模型、工具被拒绝，都要成为这次的结果。不得只在日志里出现，也不得为了看起来稳定而自动再跑一遍。
